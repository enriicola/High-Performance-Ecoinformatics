Eco-informatics is a modern way of conducting scientific research that enables scientists to generate
new knowledge through innovative tools and approaches. Ecology is increasingly becoming a data-intensive
science that involves acquiring, storing, and analysing large amounts of data from a range of sources,
including satellite and aerial remote sensing, instruments, sensors, and human observations. Ecologists
increasingly address large-scale questions with both scientific and social relevance, such as climate change
and its future effects on ecosystems and the ecosystem services associated with them. The topic of this
thesis project originated from a research study conducted by the Department of Earth, Environmental and Life
Sciences (DISTAV, University of Genoa). The study analyses changes in the distribution of natural habitats
in the Alps caused by future climate change in order to support decision-making on conservation planning and
prioritisation. The analysis uses Species Distribution Models, a dataset of approximately four million
records, and future climate-change scenarios based on General Circulation Models. The statistical software
R (https://www.r-project.org/) is used to generate predictions of future changes in habitat distribution and
biodiversity loss. The thesis student will improve the working script and its algorithmic functions to make
the model analysis more efficient, drawing on their knowledge and studies in computer science. This thesis
project involves interdisciplinary collaboration between DIBRIS and DISTAV, which can help produce better
scientific results.

\section{Thesis motivation}

\[
N_{\mathrm{individual\ projections}} = S \times P \times R \times A \times (1 + F)
\]
\[
N_{\mathrm{ensemble\ projections}} = S \times E \times (1 + F)
\]
\[
N_{\mathrm{total\ projections}} = N_{\mathrm{individual\ projections}} + N_{\mathrm{ensemble\ projections}}
\]

Here, $S$ is the number of species, $P$ the number of pseudo-absence repetitions, $R$ the number of cross-validation repetitions, $A$ the number of modelling algorithms, $E$ the number of ensemble algorithms, and $F$ the number of future scenarios. Each pseudo-absence dataset is split $R$ times, and every algorithm is fitted to each resulting combination. Each fitted model is then used to make one raster map for the current environment and one raster map for every future scenario. The ensemble models are projected in the same way. A raster is a digital map divided into a regular grid. Each of the 63,951,097 cells represents one location and stores a numerical value. In a projection raster, that value is the prediction made by one fitted model for that location. A projection map applies one fitted model to all cells of one set of environmental rasters. The count therefore measures pairs of fitted models and environmental raster sets, rather than occurrence records or explicit iterations of the R loop. With the current F/F storage configuration, each pair is written as one raw prediction raster.

The production configuration uses ten pseudo-absence repetitions, five cross-validation repetitions and five modelling algorithms. Each species therefore has $10 \times 5 \times 5 = 250$ individual models. Projecting them over the current environment and eight future scenarios gives $250 \times (1 + 8) = 2{,}250$ individual projection maps per species. Across 167 species, this gives
\[
167 \times 10 \times 5 \times 5 \times (1 + 8) = 375{,}750
\]
individual projection maps. The two ensemble algorithms add $167 \times 2 \times (1 + 8) = 3{,}006$ ensemble projection maps, for $378{,}756$ model-projection combinations in total.

The current workflow models 167 Alpine grassland species from 2,583,359 presence records. Its environmental rasters contain 63,951,097 cells and five variables. For each species, the production configuration calibrates five algorithms and builds two ensemble models. It projects these models onto the current environment and eight future climate scenarios. The workload combines a large spatial domain with repeated model calibration and raster projection.

The computational method determines whether the analysis can be completed at this scale. Historical runs lasted many hours. Several ended because of memory exhaustion, failed process forks, time limits, or file-writing collisions. Running the script on an HPC system does not solve these problems by itself. The software must control memory use, raster storage, and the scheduling of independent species.

This thesis examines the R workflow as HPC software. Leonardo provides the execution platform and the environment for measuring the program under different hardware allocations. CPU count, available RAM, storage policy, and filesystem activity affect runtime and completion. Our aim is to reduce execution time while preserving the scientific configuration, reproducibility, and output structure required by the ecological study.

\section{Objectives and contribution}

The scientific model and its parameters originate from the DISTAV study. This thesis contributes the software and experimental work required to execute that model at production scale. We adapted the R workflow to Leonardo and packaged its dependencies in a Singularity container. Each Slurm array task processes one species. We added runtime configuration, phase timings, resource measurements, success markers, and output checks. We also diagnosed memory, process-fork, and concurrent-write failures. We then compared worker counts and BIOMOD2 storage modes.

The first objective is to establish a reproducible baseline. Timings from runs with different inputs and parameters cannot provide such a baseline. The experiments identify the phases that dominate runtime. They also measure how worker count and storage settings affect elapsed time and memory. These measurements support later work on model parallelism and raster I/O. The thesis focuses on software performance. The ecological validity of the model choices and evaluation metrics remains under review with the DISTAV collaborators.

\section{Preliminary evaluation method}

The evaluation separates controlled benchmarks from historical and diagnostic runs. Controlled comparisons keep the species, input data, random seed, and scientific parameters fixed. Each comparison changes one execution setting. For every run, we record wall time, phase timings, CPU use, MaxRSS, completion status, and output validation. Failed, cancelled, and incomplete jobs show the resource limits of a configuration. We retain them as evidence but do not use them as successful performance measurements.
